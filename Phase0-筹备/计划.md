## 三、技术方案与关键决策

### 3.1 核心链路

```
技术验证链路（T0-3~T0-5，纯 Python/POC，先于 Unity 落地）：
用户输入 → 人设 Prompt 组装 → 本地 LLM 流式输出 → 「像不像猫」人工评测
用户输入 → 情绪分类（细粒度 + 强度 + 置信度） → 兜底规则
对话文本 → 记忆抽取（结构化事实）→ Embedding 向量化 → 本地余弦检索 → 注入上下文

落地链路（T0-6~T0-7，Unity 骨架）：
Unity(UI) → C# 调用 → 本地 AI 引擎(LLMUnity/GGUF) → SQLite 落库
```

### 3.2 关键决策点

- **先 Python POC 后 Unity 落地**：AI 能力（LLM/情绪/记忆）先用 Python 脚本快速验证效果，验证通过再接入 Unity，避免在 Unity 里反复调试模型。
- **人设 Prompt 是核心风险**：猫咪「像不像一只猫」决定产品成败，T0-3 必须尽早做并产出可复用的 System Prompt 模板。
- **记忆数据结构预留归属标记**（用户级/猫级）：多猫共存是 P2 才做，但数据结构在 T0-7 就定好归属字段，避免返工（对应流程路线 §十二风险）。
- **纯本地基线，云端可选**：默认本地 LLM，云端大模型仅作为「联网时可选增强」，离线回落本地，不破坏离线可用性。

## 四、开发顺序与里程碑节点

1. **W1 前半**：T0-1 PRD → T0-2 技术选型确认 → T0-9 环境搭建（并行）
2. **W1 后半**：T0-3 LLM 对话 + 人设 Prompt 原型验证（核心）
3. **W2 前半**：T0-4 情绪识别 + T0-5 记忆抽取注入 POC（核心）
4. **W2 后半**：T0-6 脚手架 + T0-7 SQLite 建模 + T0-8 CI/CD（P1）
5. **M0 验收点**：本地 AI 引擎 + LLM 端到端对话在 Unity 脚手架内跑通

## 五、验收标准（Definition of Done）

- [x] PRD 终稿完成并通过评审，功能需求含可验证的验收标准
- [x] 技术选型冻结，关键风险有明确兜底方案
- [x] 人设 Prompt 原型通过人工评测（猫咪「像一只猫」达可用基线）
- [x] 情绪识别在评测集上达可用准确率（细粒度 + 强度）
- [x] 记忆抽取→向量化→检索注入 POC 跑通
- [x] Unity 脚手架 + 本地 AI 引擎端到端对话成功（M0）
- [x] SQLite 核心表建模完成，含归属标记与迁移方案
- [x] 本地开发环境可复现搭建（含环境说明文档）

> 每一条都要「可验证」，对应 [`../合并代码.md`](../合并代码.md) 的测试用例。
> **跨功能一致性**：T0-6/T0-7 涉及「AI 引擎 ↔ SQLite ↔ Unity」多模块衔接，验收时补一条「端到端联调」项。

## 六、风险与应对

| 风险 | 应对 |
|------|------|
| LLM 人设效果不达预期（不像猫） | T0-3 尽早做原型，Prompt 迭代 + 换模型兜底 |
| 本地模型性能不足（低配卡顿） | 量化分层、延迟生成、轻量模型先可用 |
| 情绪识别误判 | 规则/词典兜底 + 人工评测集 |
| 记忆检索质量差 | 调优 Embedding + 抽取策略 |
| Unity 环境/LLMUnity 接入坑多 | 先 Python POC 验证模型可用，再进 Unity |
